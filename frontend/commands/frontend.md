# /frontend 命令

当前 skill 的**唯一主命令**。一个命令、两种用法：

1. `/frontend <需求描述>` — 根据用户需求自动查询知识库，召回匹配的知识点并编排为可直接交给大模型的实施提示词。
2. `/frontend <页面路径>` — 读取已有页面，分析其功能与上下文，匹配需要用到的知识库条目并编排为可直接交给大模型进行改造的提示词。

`/frontend` 同时承担原 `/frontend:analyze`（页面分析+方案编排）和 `/frontend:knowledge`（关键词搜索+知识匹配）的全部能力。

## 执行模式（Execution Modes）

`/frontend` 默认走 **auto-execute**（自动执行）模式：召回知识 + 生成 Agent 实施提示词 + 立即进入代码改造，**不再强制等待用户确认**。如果需要回到旧式"生成后暂停"的行为，用下面任一开关。

| 模式 | 触发方式 | 行为 |
|------|---------|------|
| `auto-execute`（默认） | `/frontend 首页` | 输出 prompt 后直接开始修改代码，跑测试、查看错误、自我修复 |
| `confirm` | `/frontend 首页 --confirm` | 生成 prompt 后**暂停**，把 prompt 摆出来等你按确认再继续 |
| `dry-run` | `/frontend 首页 --dry-run` | 只输出 prompt + 页面分析报告，**不动任何文件、不跑任何命令** |
| `quiet` | `/frontend 首页 --quiet` | 同 auto-execute，但所有中间过程压缩成最少输出（适合批量场景） |

开关可叠加：`/frontend 首页 --dry-run --quiet` 表示"预览且不啰嗦"。

### 危险命令拦截（Dangerous Commands）

无论走哪种执行模式，下列动作**必须先列出来让用户确认一次**（不论是不是默认自动执行）：

```text
- 装/卸载依赖：npm install / yarn add / pnpm add / pip install / bundle add / cargo add ...
- 跑构建/打包：npm run build / yarn build / webpack / vite build ...
- 部署相关：vercel / netlify / firebase deploy / docker push / kubectl apply / ssh ...
- 推送代码：git push / git push --force / git push --tags ...
- 破坏性操作：rm -rf / git reset --hard / git clean -fd / drop database / DROP TABLE ...
- 改全局配置：npm config / git config --global / 修改 ~/.bashrc ~/.zshrc ...
- 改 CI/CD：.github/workflows/* / .gitlab-ci.yml / Jenkinsfile 等
- 提交到 main / master / production 分支
- 任何 --force / --hard / --no-verify / --skip-tests / --allow-empty 等绕过校验的开关
```

拦截策略：

- AI 在执行上述命令**之前**必须列出命令、影响范围、是否可回滚，等用户输入 `y / yes / 继续 / 确认` 才执行。
- 若用户已经通过 `--confirm` 显式开启确认模式，则每个上述命令仍需二次确认，不被默认放行。
- 已有项目内 `npm run dev` / `npm run lint` / `npm run test` 等**幂等且无外部副作用**的命令不拦截，直接跑。
- 给出"可撤销"清单（如 `git checkout .`、`git stash`、`npm uninstall xxx`），让用户在执行危险动作前能看到回滚路径。

### 执行阶段检查点

auto-execute 模式把"召回 + 编排 + 实现 + 验证"合并为一次连续动作，但内部仍按阶段推进，阶段之间 AI 自检（**不需要用户参与**）：

```text
Stage 1  召回与编排 → 输出 prompt（含目标、技术栈、要点清单、实施顺序、验收）
Stage 2  上下文读取 → 读取页面/项目，识别约束
Stage 3  计划暴露 → 把"准备改哪些文件 / 跑哪些命令"先列出来（不执行）
Stage 4  实施 → 改代码，期间危险命令先停
Stage 5  自检 → 跑 lint / type-check / build，按需自动修复
Stage 6  报告 → 给出"改了 X 个文件 / 跑了 Y 个命令 / 验证 Z 通过"的总结
```

如果任何阶段失败（lint 不过 / build 报红），AI 自动尝试修复（≤3 次），失败后停下来报告并等待用户。

## 命令格式

```text
/frontend <需求描述 | 页面路径>
```

示例：

```text
/frontend 实现一个带入场动画的筛选表格页面
/frontend 优化卡片列表的过渡动画
/frontend 给登录页加上暗色模式
/frontend src/pages/ParcelManagement/index.tsx
/frontend src/pages/CustomerList/index.tsx
```

执行命令前必须先识别输入意图，再决定走哪条分支：

```text
输入

┌──────────────────────────────────────────────────────┐
│ Step 1：判断输入类型                                │

│ │    → 命中"页面路径分支"                          │
│ │    → 必须能读到页面入口，否则自动降级为需求描述分支并列出证据缺口 │
│ │                                                   │
│ └── 否则                                            │
│      → 命中"需求描述分支"                          │
│      → 把整段输入视为自然语言需求                  │
└──────────────┬───────────────────────────────────────┘
               ↓
┌──────────────────────────────────────────────────────┐
│ Step 2：选择召回模式                                │
│                                                    │
│ ├── 需求描述分支                                   │
│ │    → 跨域关键词+语义召回（L1-L5）                │
│ │    → 关键词改写 + 同义词扩展                     │
│ │    → 跨域推荐（自动识别跨域需求）                │
```

判断优先级：

- 输入中存在项目相对路径或绝对路径、且该路径文件可读 → 视为"页面路径分支"
- 输入是自然语言描述、关键词、技术名词或需求场景 → 视为"需求描述分支"
- 同一输入同时包含路径和需求时，**优先页面路径分支**（路径即硬证据），把需求作为补充描述

## 分支一：需求描述（`/frontend <需求>`）

### 适用场景

- 开发时需要参考某个效果怎么实现并直接生成可执行提示词
- 想让大模型按知识库里的最佳实践实现某个新功能
- 需要优化某个交互、动效、布局或主题并交给大模型落地
- 需要对比不同技术方案并把推荐结论编排进提示词
- 搜索词很短或很模糊，但希望一次性得到可用的提示词

不适用场景：

- 需要创建新的知识条目 → 用 `/frontend:distill`
- 需要验证或审查知识质量 → 用 `/frontend:distill verify`
- 需要查看知识库目录结构 → 用 `/frontend:list`

### 多层召回架构

按 `knowledge/索引/L1-L5` 分层召回，确保高召回率和准确性：

```text
用户输入: "换页动画"
    ↓
┌─────────────────────────────────────────────────────┐
│ L1：精确匹配 (100%)                                │
│ → 匹配：title、filename、精确关键词表              │
└─────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────┐
│ L2：语义匹配 (90%)                                 │
│ → 关键词改写："换页" → "页面过渡"                  │
│ → 同义词：页面切换 / 转场 / 路由切换               │
└─────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────┐
│ L3：扩展匹配 (80%)                                 │
│ → 语义变体、标签匹配、L3 标签索引                  │
└─────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────┐
│ L4：组合匹配 (60%)                                 │
│ → 多关键词组合、跨域匹配、技术栈+功能              │
└─────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────┐
│ L5：场景推荐 (40%)                                 │
│ → 场景索引、知识图谱、潜在需求推荐                 │
└─────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────┐
│ 结果合并与排序                                     │
│ Score = 精确×0.4 + 语义×0.3 + 标签×0.2 + 相关×0.1 │
│ → Top N 推荐 + 跨域补充 + 关联推荐                │
└─────────────────────────────────────────────────────┘
```

### 查询解析

#### 关键词提取

```text
1. 直接提取
   "页面过渡动画" → ["页面过渡", "动画"]

2. 技术栈提取
   "React虚拟列表" → ["虚拟列表"], tech: ["react"]

3. 场景词提取
   "列表很卡" → ["列表"], scenario: "性能问题"

4. 意图词提取
   "怎么做" → ["实现"], intent: "how-to"
   "哪个好" → ["对比"], intent: "compare"
   "优化" / "改造" / "升级" → intent: "improve"
   "实现" / "新增" / "添加" → intent: "implement"
```

#### 查询改写

```text
1. 口语化改写
   "换页" → "页面过渡"
   "很卡" → "性能问题"

2. 模糊化改写
   "页面切换带动画" → "页面过渡"

3. 技术术语规范化
   "vl" → "虚拟列表"
   "virtual" → "虚拟列表"

4. 意图补全
   "优化列表" → "列表性能优化 + 虚拟列表"
   "加暗色" → "主题切换 + 色彩系统"
```

## 分支二：页面路径（`/frontend <页面路径>`）

### 适用场景

- 页面已有功能，但缺少布局、排版、背景分区、视觉层级
- 需要根据真实页面内容生成重构实施方案
- 需要同时匹配布局、功能、动效、设计主题和项目规范知识
- 需要为另一个实现 Agent 生成自包含提示词
- 需要保留现有业务逻辑、数据契约和交互结果的前提下做改造

不适用场景：

- 查找单个技术知识（仍走需求描述分支的搜索能力）
- 蒸馏知识或直接修改页面

### 核心原则

1. 先理解项目和页面事实，再检索知识
2. 页面方案由布局、功能、动效、设计主题和项目规范共同组成
3. 广泛召回知识，严格裁剪结果，不把召回内容全部塞入方案
4. 每条知识必须绑定具体页面模块、交互链路或页面状态
5. 项目已有设计和组件优先，不重复造轮子
6. 保留业务逻辑，不凭空增加业务功能
7. 动效必须服务于反馈、连续性或空间关系
8. 背景分区必须服务于信息层级，不能只做装饰

### 决策优先级

业务逻辑、数据契约、权限、路由结果和既有交互结果属于硬约束，设计规范、UI 组件和知识建议不得覆盖。用户明确要求改变这些硬约束时，必须标记为超出本命令的页面设计分析范围。

在不改变硬约束的前提下，同一维度发生冲突时按以下顺序决策：

```text
用户明确要求
> 项目设计规范和 Design Token
> 项目已有 UI 库、公共容器和可复用组件
> 当前页面业务逻辑和交互约束
> Skill 中经过验证的知识
> 通用前端最佳实践
> 模型自由发挥
```

低优先级来源不得覆盖高优先级事实。无法消解的冲突必须写入报告，不得静默选择。

### 上下文读取范围

#### 必须读取

1. 用户指定页面
2. 页面直接引用的本地组件、样式、类型、Hooks、工具和配置
3. 项目依赖清单和当前技术栈
4. 项目中的 `design.md`、`DESIGN.md`、设计令牌、主题配置、全局样式和 UI 库配置
5. 公共页面容器、导航、侧栏、卡片、表格、表单、弹窗、抽屉及同类页面实现

#### 读取边界

- 递归读取直接依赖，直到足以识别页面功能和可复用组件
- 第三方依赖只确认项目是否已安装和已有用法，不展开读取依赖源码
- 优先搜索同类页面和公共组件，不遍历无关业务目录
- 未找到设计文档时，继续检查 Token、主题、全局样式和已有页面，不把"未找到文档"理解为"没有设计系统"
- 无法读取必要文件时，在报告中列出证据缺口并降低结论置信度

### 阶段一：建立项目约束

输出项目约束清单：

- 技术栈和版本线索
- UI 库及其现有使用方式
- 公共页面骨架和容器
- Design Token、颜色、字体、间距、圆角、阴影和断点
- 既有动效封装和减少动态效果策略
- 可复用组件
- 禁止替换或必须保留的实现

对每条结论记录来源文件。没有文件证据时标记为推断。

页面类型不能仅根据关键词判断，必须综合核心任务、主要内容、模块关系和交互密度。

对存在筛选、排序、分页、选择、主从详情或异步请求的页面，必须进一步提取可测试的状态协作不变量：哪个状态是请求参数的唯一来源、哪些变化需要重置页码或选择、详情在查询上下文变化后保留还是关闭、列表和详情是否使用独立状态通道。URL 状态只检查现有角色，不得默认新增同步行为。

请求竞态分析至少检查取消机制、过期响应保护、最新请求对 `data`、`error` 和 `loading` 的所有权、主动取消的错误处理、卸载或关闭后的更新，以及列表与详情请求是否隔离。

对 Drawer、Dialog、Popover 等覆盖层，必须描述焦点进入、焦点约束、键盘关闭、关闭后返回和原触发器卸载时的回退目标。不得以"支持键盘"代替完整焦点闭环。

### 阶段三：生成多域检索查询

基于同一个页面语义模型，为各域分别生成查询，不使用一条混合查询代替多域检索。

#### 布局域

查询页面模式、页面骨架、内容编排和响应式布局技术。重点使用核心任务、模块关系、同时可见要求、主从关系、信息密度和主画布需求。

#### 功能域

按每项 capability、关键交互链路和必要状态分别查询。区分：

- 已有功能：寻找组织方式、边界条件和改进知识
- 缺失但必要的状态：作为必须补齐项
- 无关扩展：排除

#### 动效域

按"触发器、对象、目的"查询。候选动效必须绑定状态变化、空间关系、内容连续性或操作反馈。

#### 设计主题域

查询排版、色彩、表面层级、背景分区、信息密度和反模式。项目 Token 和设计规范始终优先。

#### 项目规范与技术选型域

查询组件复用、状态管理、请求、表单、表格、地图、图表和可访问性实践。不得推荐项目未安装的新依赖，除非现有技术无法满足且方案明确标为可选。

### 阶段四：广召回与证据记录

每个候选知识记录：

```yaml
candidate:
  name: ""
  domain: "布局 | 功能 | 动效 | 设计主题 | 项目规范 | 技术选型"
  source: ""
  binds_to: []
  solves: ""
  project_compatibility: "high | medium | low"
  necessity: "required | recommended | optional"
  conflicts: []
  evidence: []
```

尽可能召回相关知识，但不得虚构不存在的知识文件。索引提到而实体文件不存在时，标记为"索引线索"，不能视为已验证知识。

### 阶段五：重排、裁剪与冲突消解

依据以下因素综合排序：

```text
来源可信度
+ 页面相关度
+ 项目兼容度
+ 实施必要度
```

结果必须分组：

- `selected`：直接进入方案
- `optional`：明确收益和采用条件
- `rejected`：记录排除理由
- `missing`：页面需要但知识库没有可靠覆盖

必须排除：

- 与核心用户任务无关的功能
- 项目已有能力的重复实现
- 与项目设计系统冲突的通用样式
- 无业务目的的装饰动效
- 只因关键词相似而召回的知识
- 会破坏业务逻辑、数据流或可访问性的方案

### 阶段六：跨域编排

不得按知识域简单罗列结果。把知识绑定到具体模块和交互链路，形成可执行指令。

编排单元包含：

```yaml
solution_unit:
  module: ""
  user_goal: ""
  layout: ""
  feature_behavior: ""
  states: []
  motion: ""
  visual_treatment: ""
  reusable_project_assets: []
  source_knowledge: []
  acceptance: []
```

例如，布局知识中的右侧详情面板、功能知识中的行选择、动效知识中的空间进入、设计知识中的表面层级和项目已有 Drawer，必须合并为一条模块级实施指令，而不是五条独立建议。

### 阶段七：完整性缺口检查

至少检查：

- 首次加载、局部刷新和提交等待
- 首次加载与局部刷新是否采用不同策略；局部刷新失败时是否保留已有数据
- 首次空数据、筛选无结果和请求错误
- 列表、详情及其他独立请求通道的局部错误与重试边界
- 权限不足、部分数据和不可用操作
- 成功反馈、失败恢复和破坏性操作确认
- 未保存更改
- 键盘操作、焦点、语义和对比度
- 减少动态效果
- 桌面、平板和移动端的结构变化与溢出

只补齐当前页面确实需要的状态。增强型建议不得伪装成必需功能。

### 阶段八：生成最终产物

严格按照 `templates/analyze-output.md` 输出：

1. 人类可读的页面分析报告
2. 可单独复制给实现 Agent 的自包含提示词

Agent 提示词必须包含准确路径、必须阅读文件、可复用组件、保护逻辑、布局结构、模块方案、功能状态、动效绑定、视觉规则、响应式策略、实施顺序和验收标准。

### 输出形态

页面路径分支输出包含两部分：

```text
┌─────────────────────────────────────┐
│ 1. 页面分析报告（人类可读）         │
│    - 项目约束                       │
│    - 页面事实 + 模块清单            │
│    - 知识召回与裁剪                 │
│    - 最终页面方案（骨架+模块）       │
│    - 风险与证据缺口                 │
└──────────────┬──────────────────────┘
               ↓
┌─────────────────────────────────────┐
│ 2. Agent 实施提示词（可直接复制）   │
│    - 自包含、可单独执行             │
│    - 页面路径、必须阅读文件         │
│    - 项目约束、保护逻辑             │
│    - 模块级实施指令                 │
│    - 背景、状态、动效、响应式       │
│    - 实施顺序 + 验收标准            │
└─────────────────────────────────────┘
```

详细模板见 `templates/analyze-output.md`。

## 禁止行为（两个分支通用）

- 不修改页面代码或样式（如用户通过 `--confirm` / `--dry-run` 显式关闭执行，则这一条无效）
- 默认 auto-execute：生成 Agent 实施提示词后立即进入实施，但**危险命令拦截清单**（见上文）必须二次确认
- 不把知识检索结果原样堆入提示词
- 不编造项目组件、设计规则或知识文件
- 不以"现代化"为理由引入渐变、玻璃拟态、过度圆角或无目的动画
- 不要求实现 Agent 重写已经稳定工作的业务逻辑
- 不创建全新页面组件（auto-execute 只改造、改写现有代码，不主动新建文件，除非明确需求要求）
- 不根据文件名直接推断完整页面类型（必须读文件后判断）

## 完成条件（两个分支通用）

- 需求描述分支：输出召回方案列表 + 知识摘要 + Agent 实施提示词，再按 auto-execute 进入实施
- 页面路径分支：输出页面分析报告 + Agent 实施提示词，再按 auto-execute 进入实施
- 输出前执行 `verification/analyze-checklist.md` 做自检
- 页面入口无法确认、关键直接依赖无法读取或页面主要任务无法判断时，**自动降级**：按需求描述分支处理 + 标注证据缺口 + 列出受影响结论 + 给出推断方案。不再要求用户手动补充信息。
- 实施结束后输出 diff 摘要（改的文件数 + 跑过的命令 + 验证结果）
